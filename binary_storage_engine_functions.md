# BinaryStorageEngine Class Functions Documentation

The `BinaryStorageEngine` class implements the physical storage layer of the `Column-Store-Data-Storage-System`. It utilizes a fixed-width, column-oriented approach, writing custom binary files (`.bin`) to disk. 

Below is an in-depth breakdown of every function (method) within the class, its purpose, and how it contributes to the overall architecture.

---

## 1. Internal Helpers & Configuration

### `BinaryStorageEngine(String dataDir)`
*   **Purpose**: The constructor for the engine.
*   **Details**: Takes the root database directory path and appends `/tables` to it. It ensures that this global tables folder is created and accessible before any table manipulation starts.

### `getColumnPath(String table, String column)`
*   **Purpose**: File path resolution.
*   **Details**: Constructs and returns the absolute file system path for a specific column's binary file. It combines `tablesDir`, the table name, and the column name into a format like `databases/mydb/tables/users/age.bin`.

### `typeTag(String sqlType)`
*   **Purpose**: Data type mapping.
*   **Details**: Accepts an SQL data type string (e.g., `"INT"`, `"DOUBLE"`, `"BOOLEAN"`) and converts it into an internal integer constant representing that type (e.g., `TYPE_INT = 3`). This tag is critical as it instructs the rest of the engine on how to encode/decode the binary data.

### `valueWidth(int tag)`
*   **Purpose**: Determines data width without metadata.
*   **Details**: Given a type tag, it returns the number of bytes the actual data value occupies on disk. For instance, a `TYPE_INT` returns `4` bytes, a `TYPE_LONG` returns `8` bytes, and `TYPE_BIGDECIMAL` returns `20` bytes.

### `recordWidth(int tag)`
*   **Purpose**: Calculates the total physical size of a single row record.
*   **Details**: Adds 1 byte (for the tombstone flag marker) to the output of `valueWidth(tag)`. This is strictly the width of the row snippet as it exists in the binary file.

---

## 2. File Metadata & Navigation

### `readTypeTag(String path)`
*   **Purpose**: Reads the data type from an existing file.
*   **Details**: Opens a `DataInputStream` for a `.bin` file, reads the first 4 bytes (the very beginning of the header), and returns the integer representing the type tag. This is how the engine dynamically "remembers" what type of data the file holds.

### `incrementRecordCount(String path)`
*   **Purpose**: Header manipulation for row counting.
*   **Details**: Using a `RandomAccessFile`, this method jumps precisely to byte offset `4` (the start of the record count in the header), reads the 4-byte integer representing the total historical rows, increments it by 1, and overwrites the value on disk.

### `recordOffset(int tag, int physicalIndex)`
*   **Purpose**: Byte-offset math for disk seeking.
*   **Details**: Calculates exactly where to place the disk pointer to interact with a specific row. It skips the `HEADER_SIZE` (8 bytes) and multiplies the requested physical index by the `recordWidth`.

### `findPhysicalIndex(String path, int liveRowIndex)`
*   **Purpose**: Maps conceptual rows to hard disk indices.
*   **Details**: Because of logical deletions (tombstoning), the 5th *alive* row in a table might actually be the 10th *physical* record written in the binary file. This function loops through the binary file from the start, ignoring deleted rows, and counting aloud until it matches the requested `liveRowIndex`. It returns the physical position index for use with `recordOffset`.

---

## 3. Byte Encoding / Decoding

### `encode(int tag, String value)`
*   **Purpose**: Serializes a string into raw bytes.
*   **Details**: Takes string values natively generated by the `QueryParser` (like `"25.5"` or `"true"`) and uses Java types corresponding to the `tag` to translate them into perfectly-sized arrays of bytes using a `DataOutputStream` mapped to a `ByteArrayOutputStream`. 

### `decode(int tag, DataInputStream dis)`
*   **Purpose**: Deserializes raw bytes back into readable strings.
*   **Details**: The inverse of `encode`. Assuming the read pointer of the `DataInputStream` is sitting squarely on the data section of a record, it consumes the exact number of bytes necessary for the type tag (e.g., `dis.readDouble()` for `TYPE_DOUBLE`) and parses it back to its String representation.

## 4. `StorageEngine` Interface Implementations

### `createTable(TableSchema schema)`
*   **Purpose**: Storage initialization for DD statements.
*   **Details**: Creates a directory for the table. It iterates over every column defined in the schema, resolves the type tag, creates a `.bin` file for that column, and seeds it with an empty 8-byte header (the type tag, and a record count of `0`).

### `appendValue(String table, String column, String value)`
*   **Purpose**: Inserts atomic data.
*   **Details**: Resolves the encoding tag, converts the value to a byte array via `encode()`, and appends two things to the end of the column's file using an appending `FileOutputStream`: the `ALIVE` marker (`0x00`), and the encoded byte array. Finally, it invokes `incrementRecordCount()`.

### `readColumn(String table, String column)`
*   **Purpose**: Sequential data retrieval.
*   **Details**: Sweeps through the target binary file top-to-bottom. It bypasses the 8-byte header, and for each record in the file, it reads the 1-byte tombstone. If the tombstone is `0xFF` (deleted), it triggers `dis.skip()` to jump precisely over the data chunk. If `0x00` (alive), it calls `decode()` and adds the string to the returning array list.

### `updateValue(String table, String column, int rowIndex, String value)`
*   **Purpose**: Direct byte overwriting.
*   **Details**: Relies on `findPhysicalIndex()` to locate the actual physical position of the "alive" `rowIndex` specified by the query engine. Using a `RandomAccessFile`, it seeks to the exact `offset` calculated for that physical index, skips 1 byte to purposefully avoid overwriting the tombstone marker, and writes the newly `encoded()` byte array on top of the old data payload.

### `deleteRow(String table, int rowIndex)`
*   **Purpose**: Performs logical tombstones.
*   **Details**: Given an integer row index from a `DELETE` query, this function sweeps across *every single column file* inside a table's directory. It identifies the target physical offset, opens a `RandomAccessFile`, seeks to that physical offset, and writes a single `0xFF` byte directly onto the tombstone slot. The actual data payload adjacent to the tombstone is safely untouched, but rendering it invisible to future read operations.

### `dropTable(String table)`
*   **Purpose**: Complete structural destruction.
*   **Details**: Calls `FileUtils` to recursively delete the root sub-directory dedicated to the table name within `databases/<db_name>/tables/`, effectively wiping out all associated `.bin` components and data traces from the drive.
